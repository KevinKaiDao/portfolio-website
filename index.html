01 — About

Between hardware and software

I'm a fifth-year Computer Engineering student at Toronto Metropolitan University, graduating in May 2027. Computer engineering sits on the line between hardware and software, and that line is the part I actually enjoy — I'd rather understand a system from the sensor up to the interface than specialize in one slice of it.

That shows up in what I build. I've written PID logic in structured text and pushed it across OPC UA into a SCADA screen; built image recognition in Python with OpenCV and TensorFlow; shipped a Node.js bot serving live transit data to real users; designed relational schemas in SQL and digital logic in VHDL; and written C close to the metal. Different tools, same instinct — work out what the system is really doing, then make it do the right thing reliably.

Alongside that I spent 16 months in the field with ProAutomated, commissioning building automation systems in data centers across the U.S. That taught me things a lecture hall can't: how systems fail in practice, how much of engineering is careful documentation, and how to explain a problem clearly to the people depending on the answer.

I'm drawn to work where hardware and software meet — software development, embedded systems, test and integration, controls and automation — and I'm happy anywhere I get to learn a new stack quickly.

Featured · Controls

Tank PID Control System

A full closed-loop level control system built end to end: a soft PLC running a PID loop on a 100 ms cyclic task holds a water tank at an operator-entered setpoint by modulating pump speed, and an Ignition Perspective HMI gives the operator the numbers and the alarms.

The whole thing runs on a deliberately small contract — five tags across the OPC UA boundary. Level and setpoint are both normalized to 0–100% in the PLC, so the HMI never needs to know the tank's geometry; swap the vessel and only the PLC scaling changes. The comms tile watches the subscription quality directly and goes red the moment the link drops, so a dead connection reads as a fault rather than a screen of stale numbers.

  • CODESYS
  • Structured Text
  • PID control
  • OPC UA
  • Ignition Perspective

GO Transit Data Bot

A Discord bot that pulls live GO Transit schedules, routes and service alerts through REST APIs so riders can check departures without leaving chat. Async request handling cut average response time from 500 ms to 350 ms, and a caching layer removed about half the redundant API calls. It serves 50+ users in a live server, handling 100+ queries a day.
